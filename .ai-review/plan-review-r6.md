## 1. 需求與邊界缺漏

**R6-1｜facetNormalize 的「內部空白」沒有封閉定義**

- **嚴重度：Medium**
- **問題：** §6.0 封閉的是 `strip` 的字元集合，新增的「內部連續空白壓為單一空格」未明確引用同一集合。兩種實作可以同樣遵守尾端 `strip`，卻對內部 U+001C～U+001E、U+200B／U+FEFF 等產生不同分組。ETL 單端計算消除了跨 runtime 重算，沒有消除這項規格歧義。
- **為什麼現在不修之後會更貴：** 分組鍵同時是 bucket 值與 URL 值；日後修正字元範圍會再次移動 Trial 分組、使分享連結失效。
- **建議修法：** 明定壓縮步驟使用 §6.0 的 `White_Space=Yes` 集合，輸出單一 U+0020；零寬字元及集合外控制字元不因本步驟被刪除或替換。驗收分別涵蓋前後、內部及集合外反例，不能只驗尾隨 TAB。

**R6-2｜非空 typed 正規化成空鍵時，歸類沒有定案**

- **嚴重度：Medium**
- **問題：** §9.3.3 只明定空字串的 typed 為 null；`" \t\r\n"`、NBSP-only、U+3000-only 可以是非空 typed，但經 §6.0 得到空字串。§8.4「空 → 未提供」未指明檢查哪一層。照 §9.3.5 分組可產生空字串 bucket；若把它歸「未提供」，I6 又禁止未提供者帶 `facetKeys`，前端缺少一份明確的分類契約。
- **為什麼現在不修之後會更貴：** ETL、統計與前端可能各自選擇不同的空值判準；總數仍閉合，卻出現空白選項或「未提供」漏列。
- **建議修法：** 封存順序與結果：先判衝突，再判 typed null，再判正規化結果是否為空。建議正規化空鍵歸「未提供」、禁止空值 bucket，並同步定義這種情況的 `facetKeys` 表示與前端判讀方式。raw 與文字 sentinel 的保存規則維持不變。另涵蓋「來源非零列，但 applicant 全部未提供／衝突」；來源零列仍依既有 B3 硬失敗。

**R6-3｜§7.1 仍要求直接用 typed 篩選，與新增傳輸契約不一致**

- **嚴重度：Low**
- **問題：** §7.1 表格仍寫「篩選：`displayFields` 的 typed 值」（第 443 行），但 §9.3.5 已要求 applicant 使用 ETL 提供的分組鍵。另 §6.4.4 的 `{欄位名: 分組鍵}` 未像其他 schema 一樣明列鍵名，且其省略條件直接寫 `facetNormalize(typed)`，容易被誤讀為所有 facet 都適用。
- **為什麼現在不修之後會更貴：** 依呈現層摘要重建前端，便可能重新引入本次要修的漏報；不同讀取端也可能分別使用 `applicant` 與來源中文欄名。
- **建議修法：** §7.1 直接引用 §9.3.5；封閉 `facetKeys` 的允許鍵為 `臨床試驗申請者`，明定省略時使用還原後 typed、不得省略必要差異鍵、不得出現額外鍵或空物件。`phase`／`scale` 明確維持合法 typed 常數。

**R6-4｜舊 URL 的延期處理，不能被解讀為允許靜默零結果**

- **嚴重度：Medium**
- **問題：** §15 明列舊旁支 raw URL 延後處理，但 §7.4 已要求無效值顯示明確訊息、不得靜默丟棄。現在沒有明確說明：「格式合法但已不在 applicant bucket 的舊值」是否屬於該無效值路徑。
- **為什麼現在不修之後會更貴：** v3 上線後，既有連結可能顯示普通零結果，讓使用者誤認該申請者沒有試驗；schemaVersion gate 無法辨識 URL 的舊語意。
- **建議修法：** **不要求本輪新增舊值自動遷移。** 只需明定這類值適用 §7.4 的既有失效提示，且 §15 的延期不豁免此行為。D4 指名純舊值及「有效值＋失效舊值」兩種情況，禁止靜默忽略後者。

## 2. 架構風險

**R6-5｜最難回頭的是公開分組鍵語意；manifest 範例仍停在版本 1**

- **嚴重度：Low**
- **問題：** §9.3.5 的 manifest 範例仍為 `schemaVersion: 1`（第 686 行），與 v0.10 首段及 §15 的版本 3 不一致。§9.3.6 的舊豁免已附失效條件，因此不是要求重新討論 bump；問題是現行輸出契約範例仍可能被當作依據。
- **為什麼現在不修之後會更貴：** bucket 鍵已成為公開 URL 語意；錯標版本會使舊前端把新資料當成相容資料，重現旁支漏報。
- **建議修法：** 更新現行範例為 3，將版本 1 說明明確標為歷史。沿用已聲明的資料先行、三處對齊 gate 與同 commit 原子部署，不另設遷移架構；bump 後暫時 CI 紅不列為缺陷。

**R6-6｜稀疏 facetKeys 合理，但 F1 通過不能替代稀疏性驗收**

- **嚴重度：Medium**
- **問題：** §6.4.4 已要求稀疏輸出，但 §11 沒有專門保證其必要且充分條件。把每筆 Trial 都附上相同於 typed 的鍵，仍可能在目前快照通過 F1；因此「未超標」不代表符合資料契約。
- **為什麼現在不修之後會更貴：** index 已佔 Tier 0 的 98%；冗餘欄位擴散後才回收，會牽動產生端、讀取端與既有 artifact。
- **建議修法：** 稀疏性由 I6／B6 獨立驗收，F1 仍量測包含 v3 artifact 的實際部署回應。保留 1,500,000 bytes 門檻及既有三檔集合，不以舊快照或 q11 估算宣告通過。§9.3.2 的兩層 digest 定義已可涵蓋新增欄位，無須改動。

## 3. 驗證策略缺口

**R6-7｜D4、E2 尚未鎖住「勾一個選項，完整取回該組 Trial」**

- **嚴重度：Medium**
- **問題／可通過的弱化實作：**
  - **D4：** 每個維度至少一組，可只選不需要正規化的 applicant；前端繼續比較 raw typed 仍通過。
  - **E2：** widget 正確顯示 stats 的完整 multiset，但篩選仍漏掉旁支 Trial，E2 仍通過。
  - 生成端與驗證端若共同漏做 NFKC，彼此對帳也不能證明分組正確。
- **為什麼現在不修之後會更貴：** 這正是本次事故的形狀；統計測試與篩選測試各自全綠，整體仍靜默漏報。
- **建議修法：** 在 §11 指名跨不同 Trial 的分組案例：前導／尾隨／前後空白、內部連續空白、NBSP、U+3000、CRLF、U+F9B3，以及三個以上變體。以固定 oracle 斷言唯一 bucket 的精確值、計數及選取後完整 trialId 集合；清空其他條件時，選取結果數須等於該 bucket 計數。D4 再驗 canonical URL 與 reload 後結果，而不只控制項。

**R6-8｜B6 對帳粒度仍是 I6，新增約束可整批漏驗**

- **嚴重度：Medium**
- **問題／可通過的弱化實作：** B6 已要求每條不變量獨立反例，但既有三個 facet 計數 mutation 就足以替 I6 掛上「已涵蓋」。一個完全不檢查 `facetKeys` 的驗證器，仍可符合這份 inventory 的最低要求。
- **為什麼現在不修之後會更貴：** 錯鍵直接決定前端漏報；digest 自洽不代表鍵正確，等到正式資料出錯才會發現整個新增檢查沒有反例保護。
- **建議修法：** B6 對 I6 明列獨立反例類別：必要鍵缺失、鍵值錯誤、與 typed 相同卻冗餘出現、衝突者帶鍵、未提供者帶鍵，以及 R6-3 定案後的額外鍵／空物件。另加入 **stats 與 facetKeys 一起被改成同一錯誤分組、typed 不變** 的反例，以殺死讀 `facetKeys` 自證的驗證器。全部沿用 digest 自洽、違規集合精確相等及正常樣本零違規要求。

**R6-9｜C1、C3、D6、E7 未完整保護新 facet 路徑的 sentinel 與衝突邊界**

- **嚴重度：Medium**
- **問題／可通過的弱化實作：**
  - **C1：** 只驗分類 sentinel；把所有 facet 都套 NFKC，仍可通過 sentinel 斷言，卻把合法 `Phase Ⅱ` 改成不符合常數的值。
  - **C3：** 驗 raw 與詳情文字；applicant 的 `N/A`、`NA` 在 facet 被錯歸「未提供」，仍可能通過。
  - **D6：** 前端正確優先判衝突即可通過，即使 artifact 仍偷偷攜帶衝突候選的 `facetKeys`。
  - **E7：** 候選值不進卡片且 `displayFields` 省略即可通過；新增的 Trial 層欄位不在其資料形狀斷言內。
- **為什麼現在不修之後會更貴：** 新欄位形成另一條候選值與分類資訊通道；舊驗收可能只守住畫面，未守住輸出契約。
- **建議修法：** 明列 phase／scale 合法值不變的正例；applicant 的 `N/A`、`NA`、空值分別定義精確 bucket／未提供結果，不能把 C1 的分類 sentinel 政策搬過來。D6／E7 交叉斷言衝突者無 `facetKeys`、只進「不一致」，並由 B6 承擔相應變造反例。

**R6-10｜A2、C5、C6、D2 沒有證明四套正規化保持獨立**

- **嚴重度：Medium**
- **問題／可通過的弱化實作：**
  - **A2：** 「同日僅空白／全半形差異」可以由其他欄位充數，不必觸及 applicant。
  - **C5：** 文字比較狀態的一組正例，不足以殺死只在 applicant 改用 `facetNormalize` 判衝突的弱化實作。
  - **C6：** 代表 raw 選得正確，facet 卻取另一筆 cohort 的值，仍可通過原本的代表值斷言。
  - **D2：** 只要求 identity／search 分開驗證；facet 偷用 search 的 casefold 仍可能通過。
- **為什麼現在不修之後會更貴：** `conflictText` 移除全部空白，facet 保留單一內部空格，兩者的等價類本來就不同。錯誤共用會改變衝突、分組或大小寫區分。
- **建議修法：** 指名 `甲 乙` 與 `甲乙`：同日比較不衝突、帶 `rawVariants`，但兩個 facet 鍵不同；本輪維持單值分組時，明確以 §6.4.3 既定代表值導出鍵，不增加多 bucket membership。另驗 `ABC`／`abc` 在 search 可同命中、facet 必須分組不同，以及零寬字元不折疊。不可為了讓測試一致而改用 `conflictText` 作 facet 鍵。

**R6-11｜新增顯示鍵的 E4 與原文呈現，缺少轉換前後的反例**

- **嚴重度：Medium**
- **問題／可通過的弱化實作：**
  - **E4：** 既有 XSS fixture 若只含 ASCII 符號，可能抓不到「先處理原文字串、再 NFKC」後新出現的 `<`、`>` 等符號。
  - **C6／E7：** 分別驗代表值及衝突呈現，不能保證非衝突 applicant 卡片仍顯示 raw；直接把分組標籤拿來顯示，這兩條仍可能通過。
- **為什麼現在不修之後會更貴：** 分組鍵已新增使用者可見 surface；日後追查會混淆「來源就是如此」與「顯示經過正規化」。
- **建議修法：** E4 增列 NFKC 後才形成特殊符號的 applicant 案例，驗證最終顯示仍是文字。另對同一筆變體明確斷言：選項／統計使用分組鍵，卡片與詳情保留 raw，不能只驗資料物件中的 raw 尚未被修改。

受影響但**無須重開契約**的驗收條件，仍應明確理解其保證範圍：

| 驗收條件 | 能通過但功能仍壞的弱化實作 | 本輪判定 |
|---|---|---|
| A3 | 穩定、可重現地拆錯 bucket | 確定性不證明分組正確，由 R6-7 補足 |
| B7 | 所有 datasetVersion 一致，但 bundle／artifact schema 語意不相容 | 沿用已聲明的三處 schema gate；B7 不能替代它 |
| B8、B9 | 穩定產出錯誤 facet，仍可重算且冪等 | digest／發布契約無須修改，語意由 I6 與固定 oracle 保護 |
| F1 | payload 很小，但篩選漏掉旁支 | 原門檻足夠；通過效能驗收不能代替 D4／E2 |

## 4. 更簡單的替代方案

**R6-12｜可簡化契約表達，不宜改成另一套資料架構**

- **嚴重度：Low**
- **問題：** 目前 `facetKeys` 看起來像通用多欄位機制，但 v0.10 實際只授權 applicant，增加了讀者自行推廣至其他欄位的空間；這是契約表達問題，尚不構成 over-engineering。
- **為什麼現在不修之後會更貴：** 一旦不同產生端自行增加鍵，之後再收回會涉及 schema、驗證器及 payload 相容性。
- **建議修法：** 保留稀疏 `facetKeys`，把它寫成只有 applicant 的封閉契約及一份分類決策表，其他章節引用即可。前端自行正規化違反已聲明的 runtime 邊界；改寫共用 typed 會擴大本輪影響；全量附鍵增加 F1 成本；另建 alias 字典增加查找與一致性契約。這些替代方案均沒有明顯優於目前設計。
