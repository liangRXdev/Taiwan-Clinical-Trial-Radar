## 1. 需求與邊界缺漏

## 2. 架構風險

| # | 項目 | 嚴重度 | 判定 | 理由 |
|---|---|---|---|---|
| 2.1 | 多檔 `os.replace` 不構成整體原子發布 | High | **部分接受** | **問題屬實**——我 §6 聲稱「全部檢查通過才以 os.replace 原子替換」，對多檔輸出不成立。**但修法過重**：Codex 提議另建不可變 snapshot 目錄 + manifest 指標切換。本專案的發布邊界其實已經是原子的——資料進 git commit、Cloudflare Pages 部署的是**一個 commit** 而非個別檔案。所以正確修法是把 promotion 邊界定義為 commit：build 全部寫進 working tree 並驗證整體 digest 與 referential integrity 後才 commit，中途失敗即不 commit。不需要 snapshot 目錄與指標切換，少一層元件。 |
| 2.2 | `builtAt` 與「無變動不 commit」互相矛盾 | High | **接受** | 屬實且是我 v0.2 內部的真矛盾：§6 要求每次寫 `builtAt`，H2／H3 又要求第二次跑不產生 commit——兩者不可能同時成立。修法（`builtAt` 語意改為「目前已發布 artifact 的建置時間」，來源無變化則不發布也不更新）正確。 |
| 2.3 | Trial／Revision 缺少完整輸出契約 | High | **接受** | 屬實。revision ID、Trial→shard 映射、`latest` 是嵌入或 reference、排序 total order、schemaVersion 升級條件、referential integrity 都沒寫。兩層概念對，但不足以驗收。 |
| 2.4 | Cloudflare Pages 路由策略未定案 | Medium | **接受** | 屬實。D4 只測 query state，證明不了詳情頁 deep link 與重新整理可用。須選定 canonical URL 形狀並定義未知 Trial ID 的行為。 |
| 2.5 | 最難回頭的決策排序 | High | **接受** | 屬實。最難回頭的是「identity normalization + 單值 latest + URL/shard identity」組合，不是 Cloudflare Pages。同時確認四項定案（只做 205、純靜態、無 PWA、Cloudflare Pages）與限制相容、無須翻案——這點與我的判斷一致。 |

## 判定者獨立性的已知限制

本判定由規劃者本人（撰寫 v0.2 的同一個 agent）執行，不是獨立第三方。依 `codex_dual_review_workflow` 的經驗，規格與實作由同一人先後撰寫會漂移，而兩輪審查中間那道縫只有「規格符合度稽核」補得到。

本輪特別值得記錄的是：**56 項中有 11 項是 v0.2 修訂自己造出來的洞**（1.4、1.7、2.1、2.2、A1–A6 的部分、D2 的錯誤舉例、D4 的矛盾案例、E3 的弱斷言、E5 的漏帶、F3 的錯數字、4.4 的範圍膨脹），與過往「第一輪修訂自造 4 個洞」的模式一致。這證明第二輪審查必須存在，且**只審修訂本身**。

因此：v0.3 完成後須重跑 `/codex-checkplan`，且第二輪只審 v0.2 → v0.3 的變更。
