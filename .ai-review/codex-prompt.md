# 獨立覆審請求：Taiwan-Clinical-Trial-Radar（M4 規格符合度稽核）

**唯讀模式。禁止寫入或修改任何檔案，只輸出報告文字。**

專案已完成 M0–M3 並上線。本次覆審的重點是**規格符合度**：規格經五輪覆審定案，
實作與測試也都寫完了，但**沒有人逐條比對過兩者**。

## 專案前提 (a)：架構限制與刻意取捨

以下設計看起來像缺陷，但都是有意為之。**若你的建議與這些衝突，請明說衝突並改提相容的替代作法。**

1. **唯一具規範效力的規格是 `.ai-review/plan.md` v0.9。** `Taiwan-Clinical-Trial-Radar-spec.md`
   與 plan.md 的 v0.2–v0.8 都是歷史文件，**不得作為實作或驗收依據**。repo 根目錄的
   `CLAUDE.md` 目前落後（仍寫 M0.5／v0.7），那是已知的文件債，不必列為發現。

2. **只用 TFDA dataset 205。** 同系列 206–209 永久不納入——它們沒有任何可驗證的
   trial identifier。建議「補上關聯以豐富資料」一律視為誤判。

3. **同日多筆不做 tie-break。** `資料更新時間` 只有日精度、無時間無版號；實測 846 組
   平手，其中 143 組正規化後仍衝突。這些**不准挑一筆顯示**：卡片只顯示無衝突的共同
   欄位，衝突欄位完全省略（不是給 null）。建議「取最新一筆」「取非空欄位最多者」
   「依 CSV 列序」一律視為誤判——列序不是穩定契約。

4. **近似的 protocol 只揭露不自動合併**（已知 18 組）。identity 正規化刻意
   `strip → NFKC → upper`，**不剝標點、不壓內部空白**。自動合併會誤配，比重複更危險。

5. **三套正規化各自獨立**（identity／search／conflictText），刻意不共用。
   建議「抽成同一個函式以消除重複」會讓主鍵跟著查詢需求漂移，視為誤判。

6. **高密度斷言與變異哨兵是本專案的失效模式對策。** 本專案怕的是**假綠燈**
   （斷言錨錯位置、恆真斷言、sentinel 讓變異假死），不是測試過多。
   「測試可精簡」「移除重複測試案例」不是有效發現。

7. **無 runtime API、無後端、無資料庫。** 全部是 build-time 產生的靜態 JSON ＋
   瀏覽器端檢索。建議導入伺服端搜尋、資料庫、SSR 一律視為與架構衝突。

8. **前端不使用 `innerHTML`**，`src/ui/dom.ts` 是唯一 DOM 建構入口。這是刻意的。

9. **不載入任何外部資源**（含網頁字型）。2026-09-22 實測 Google Fonts 佔冷啟動
   payload 的 63%。建議加回 Google Fonts 或任何 CDN 一律視為誤判。

10. **不做 dark mode**、不做方向性版本 diff、不顯示招募狀態、不保留任何相關 feature flag。
    這些都是規格明列的「明確不做」。

## 專案前提 (b)：威脅模型與風險權重

- **沒有認證、沒有 session、沒有機密、不收任何使用者資料。** 不蒐集搜尋字串、IP 或 analytics。
- 資料是 TFDA 公開的臨床試驗審查紀錄，**使用者是臨床藥師與醫療專業人員**，
  用途是檢索試驗資訊。
- **風險排序（規格 §10 明列）：誤導 > 資料正確性 > XSS。**
  - 最嚴重的是**誤導**：同日兩筆寫 `19` 與 `31` 卻只顯示其中一個、把「約400」讀成 400、
    偽造一個資料日期、把「查無資料」呈現成「不存在」、暗示 TFDA 審查等於上市核准、
    暗示試驗正在招募。這些會讓臨床人員做出錯誤判斷。
  - **漏報比誤報嚴重**：該標示衝突而沒標示，比多標一個警示更糟。
  - XSS 排在最後，但不是可以不做——靜態站無憑證可竊，危害上限是顯示假內容，
    而顯示假內容本身又回到「誤導」那一軸。
- **攻擊者要造成危害必須先污染上游 TFDA 開放資料**，或攻破 GitHub Actions 的發布鏈。
  因此**污染資料的「入口」比污染資料的「渲染」重要**：例如停用 TLS 驗證、
  接受非 200 狀態、把 schema 驗證放寬，都比某個欄位忘記跳脫嚴重得多。
- 發布鏈的最大風險是**部分發布**：`public/data/` 被替換到一半就 commit，
  使用者會拿到由兩個版本拼出來的答案。規格 §9.2.1 要求「不存在部分發布的 commit」。

## 要求產出的四個區塊

每項發現須含「**檔案:行號 / 嚴重度(Critical|High|Medium|Low) / 問題描述 / 建議修法**」。

### 1. Code review

邏輯錯誤、安全風險、例外處理不足、可維護性問題。

其中**重複實作**須單獨列出：同一份規則／表格／轉換邏輯是否在兩處以上各寫一遍，
或既有函式已提供該能力卻另起爐灶。每項須同時引用**兩端的 file:line**，
並說明兩者漂移時會產生什麼錯誤結果。

**範圍排除**：測試檔、驗證器（validator）、規格明列的行為。這三類的重複是刻意的
縱深防禦。建議精簡此三類者一律視為誤判。

### 2. Test gap analysis

現有測試覆蓋現況，指出未涵蓋的正常流程、邊界值、失敗情境。

特別注意**恆真斷言**：一條永遠不會紅的斷言證明不了任何事。例如對「本來就不在
`displayFields` 的長文字欄位」斷言「候選值不出現在卡片」——無論衝突有沒有被偵測到
都會成立。

### 3. Dependency audit

過期、已知漏洞、不必要、授權有疑慮的依賴。Python 依賴見 `pyproject.toml`／`uv.lock`，
Node 見 `package.json`／`package-lock.json`，GitHub Actions 見 `.github/workflows/`。

### 4. 規格符合度稽核（**本次重點**）

讀 `.ai-review/plan.md` 的**驗收條件 A1–H5**（§17）與架構決策，逐條指出
**規格宣稱有、但實作實際沒做到或做弱了**的項目。特別注意這四種形態：

- **驗證只驗了較弱的性質** —— 規格說「驗證 A 與 B 一一對應」，實作只檢查 A 的檔名格式
- **宣稱的欄位從未產生** —— 前端有 `if (meta.x)`，但管線從不寫入 `x`，功能靜默不存在
- **宣稱的失敗處理未實際觸發** —— 錯誤分支存在但條件永遠不成立，或訊息與實際行為不符
- **驗收條件被抄弱** —— 規格要求「每一個 X 各有一組」，測試只涵蓋其中幾個；
  或規格要求「精確集合相等」，測試只驗了 `toContain`

這不是找新需求，是查核既有承諾。**每項須引用「規格條款編號 + 實作檔案:行號」兩端。**

另請特別檢查：

- **規格改版後沒同步的地方**。plan.md 經五輪覆審（v0.1 → v0.9），§15 記錄了每輪的修訂。
  修訂常常只改了規格文字而沒有連帶改測試，或反過來。
- **§17 的 A1–H5 逐條點名**：哪些條有對應測試、哪些沒有、哪些有但驗的是較弱的性質。
  請明確列出「沒有任何測試對應」的驗收編號。
- **M3 新增的 `BASELINE_MOVED` error code**（exit 26）是否與 §9.5 的表、B1 的
  「每個 error code 各一測試」一致。
